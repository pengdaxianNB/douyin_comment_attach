# 稳定性排查报告

日期：2026-10-12。范围：启动与退出、Qt/Chromium 页面生命周期、后台调度及取消、数据库迁移与查询、AI/站点请求、界面数据展示、启动脚本、依赖锁文件和回归测试。

## 结论与现场证据

本次发现的主要风险集中在退出时强制终止 Python 线程、接口响应无限等待、旧数据库升级中途提交，以及异常配置/时间字段进入 Qt 界面。已完成第一批修复。

只读扫描现有 6 份滚动日志后发现：

| 日志特征 | 匹配次数 | 含义 |
| --- | ---: | --- |
| “内核异常” | 505 | 出现在自动恢复提示中，不能直接视为原生崩溃 |
| “超过处理时限” | 260 | 页面连接、初始化或清理超时的迹象 |
| “自动重建失败” | 23 | 这 23 条均包含“未找到该账号的内嵌页面” |
| 后台引擎异常退出、未捕获异常、Python traceback | 0 | 已留存日志没有记录这类异常 |
| 数据库锁定或损坏的指定错误文本 | 0 | 已留存日志没有匹配记录 |

这些是字符串匹配次数，可能包含重复记录；不能换算成独立故障数或软件崩溃概率。当前证据更支持优先排查页面重建、目标绑定和界面响应延迟。历史日志没有足够的原生进程诊断信息，暂时不能确定是否存在 Qt 宿主崩溃或内存不足。

数据目录大小约为：数据库 22 MB、浏览器资料 1.2 GB、截图诊断 36 MB、日志 13 MB。浏览器资料是磁盘占用，不能据此判断运行时内存泄漏。此次未修改业务数据库、浏览器登录资料或历史日志。

## 已修复的问题

| 问题与触发条件 | 原行为 | 本次调整 |
| --- | --- | --- |
| 关闭时任务仍未结束 | 20 秒后调用 `QThread.terminate()`，可能中断数据库操作或线程清理 | 直接取消主任务，先等待工作任务保存结果，再退出 Playwright；超时继续等待，保持 Qt 事件处理 |
| 登录/诊断执行中关闭，或引擎初始化时关闭 | 退出命令排在当前命令后，初始化之前的命令可能被丢弃 | 保存退出请求；直接取消正在执行的命令；为登录连接、页面置前和诊断增加超时 |
| 后台退出后用户继续操作、GUI 回执延迟到达 | 就绪标记可能残留，关闭的事件循环可能再次收到回执 | 退出时清除就绪状态、循环和请求；明确拒绝无效命令；忽略已关闭循环的迟到回执 |
| 评论/作品/指数关键词接口迟迟不结束 | JSON 读取及清理时的 `gather` 可一直等待 | JSON 读取限制为 8 秒；离开采集流程时取消未完成响应任务；评论采集在创建任务前过滤无关接口 |
| 视频表升级复制失败 | `executescript` 可能提前提交，留下部分升级后的结构；也会影响同轮账号迁移的原子性 | 账号和视频表升级统一事务，以逐条 `execute` 完成，复制失败全部回滚 |
| 配置包含坏 JSON、错误类型、极大或非正整数 | 界面构建异常，或后台并发/轮询范围失控 | 默认值回退和日志提示；后台统一约束数值范围，界面读取同一份规范化配置 |
| 视频时间超出系统可表示范围 | 定时刷新不断抛错，视频表构建失败 | 无效时间显示为空，继续展示和处理其他视频 |
| 客户/事件表增长 | 高频领取、排序和账号额度统计缺少对应索引 | 添加客户状态/更新时间、更新时间和账号事件复合索引 |
| Qt 宿主或浏览器渲染进程异常退出 | 普通 Python 异常钩子不足以诊断原生故障 | 启用 `faulthandler`、记录渲染进程退出码，并为引擎异常保存完整异常栈 |
| 重复启动与崩溃日志轮换 | 第二实例可能打开或轮换第一实例正在使用的诊断日志 | 先取得数据目录锁，再初始化日志和 QtWebEngine；重复启动直接提示 |

Qt 官方明确说明，强制终止线程可能发生在修改数据或持有互斥锁期间，无法保证清理。这是此次移除强制终止逻辑的依据：[QThread::terminate 官方说明](https://doc.qt.io/qt-6/qthread.html#terminate)。

`native-crash.log` 尽可能记录宿主进程的 Python 线程栈，不是完整的 Chromium 子进程转储；操作系统直接杀死进程、磁盘故障或部分原生错误仍可能没有记录。渲染进程异常会发出日志和提示，由已有任务异常流程决定恢复或停止；不会在该信号里直接重放发送操作。

## 后续改进顺序

### 优先级 1：减少 GUI 线程上的数据库和文件工作

`Window.refresh_runtime_views`、`refresh_accounts`、导出和备份仍在 GUI 线程同步访问数据库/文件。`DB.connect` 最长等待锁 20 秒，而浏览器协调请求最多等待 GUI 回执 15 秒。若 GUI 被阻塞，页面释放或恢复可能被误判为失败。日志中的“未找到内嵌页面”也需要结合 GUI 延迟进一步定位。

建议让独立数据库工作线程执行查询、备份和导出，仅将纯数据通过 Qt 信号交给 GUI；所有 QWidget 操作继续留在主线程。账号状态刷新也应合并，避免每条状态消息重新查询所有账号额度。验证目标：数据库繁忙、备份和大文件导出期间，界面仍可响应关闭，浏览器协调回执不被排队阻断。

### 优先级 1：为大视频列表分页，并统一预算 DOM/CDP 操作

客户表已有 1000 行上限、数据库管理页已有分页；`refresh_videos` 和部分队列仍一次读取完整视频列表。很多搜索词持续累计时，读取、Python 对象和 QTableWidgetItem 会一起增长。

建议视频表分页或改为按需加载的 QAbstractTableModel，按可见页面查询。对尚无统一超时的 DOM 查询和 CDP 操作逐步加入每步时间预算。允许大量作品的正常扫描继续进行，同时限制单个挂起调用的等待时间。

### 优先级 2：针对页面绑定失败完善生命周期观测

目前普通采集模式的页面重建采用 `browser_reset` 单向信号，私信资源调度采用带回执的 `browser_state`。建议统一为带完成回执的操作，记录请求时间、GUI 完成时间、目标 ID 和 CDP 重连耗时。复现历史的“未找到内嵌页面”后，才能区分 GUI 延迟、目标发布延迟和连接状态错误。

保留有上限的重建尝试与退避，不应在连续失败时无限重建，也不应因页面重建重放已经提交过的私信。

### 优先级 2：建立全局页面数量和运行时内存监控

已有私信工作位限制、页面休眠、周期重建和磁盘缓存上限。这些机制并不等于全局内存上限：手动打开的空闲账号页面和采集页面也会占用资源。

建议记录宿主与 Chromium 子进程 RSS、活跃页面数、重建次数和增长速度；优先回收空闲页面，在压力下减少并发。阈值根据实际电脑内存和长期运行数据设置，不能只根据资料目录大小推断。

### 优先级 3：长期压力测试和宿主故障隔离

已有测试验证功能与短周期生命周期，尚未证明 24–72 小时无人值守运行的稳定性。建议使用本地模拟页面测试反复创建/休眠/重建、慢接口、断网、数据库锁竞争和重复退出，记录内存增长与任务恢复结果，再在 Windows/macOS 的锁定依赖环境中分别回归。

如果新增诊断确认整个 Qt 宿主存在原生崩溃，再考虑把业务工作进程与界面进程进一步隔离，并通过持久队列恢复。恢复必须继续遵守现有发送保护：已记录提交但结果不明的客户不自动重发。
